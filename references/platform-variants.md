# 多平台版本：从锁定时间线派生

首发平台版本锁定后，第二个平台只换画面和版式，不复制剪辑事实。平台顺序见 SKILL.md Step 1；360 镜头
的重投影见 [`360-reframe.md`](360-reframe.md)。「观测实例」来自冈仁波齐转山 vlog（827 秒）从视频号 9:16
派生 B 站 16:9 的过程，只作观测，不作定律。标注「Skill 介绍片」的观测实例另来自一条讲本 Skill 的讲解片
（278.4 秒，竖版先发视频号，再从同一套场景代码派生横版）。

## 1. 先核对约定，再给作者选

- 进入下一个平台前，先读交付约定里的画幅和版本，确认对应版本是否已经存在。需要派生时量化工作量
  （镜头数、照片数、全片帧数），把“按约定派生”和“直接复用现有版本”两个选项连同预计耗时交给作者选。
  观测实例：71 个镜头（60 个 360 镜头、10 段手机视频、1 段旧视频）、46 张静帧、24810 帧；作者选派生
  16:9，有效工时约 5 小时。

## 2. 同一条时间线，只换画面与版式

- 时间码、混音、字幕都不动；每个变体只换画面和版式常量。变体用独立的输出目录和缓存键；改完先证明首发
  画幅的缓存键和画面都没变（观测实例：竖版 71 个缓存键逐一核对无变化）。
- 两个画幅同一条锁定时间线时，第二画幅不重新混音、不重做母带：把首发版本（已批准或已发布）成片的音频流
  原样复制（stream copy）到新画幅的视频上，让两个平台的声音逐字节一致。前提是时长、起点、帧率一致，封装前
  先核对这三项；封装后对两份文件的音频流各算一次哈希，必须相同，并用 ffprobe 核对两份音频流的 `start_time`
  与时长。观测实例（Skill 介绍片）：两版都是 278.4 秒、30 fps、AAC 48 kHz。

  ```bash
  ffmpeg -i new_video.mp4 -i published.mp4 -map 0:v:0 -map 1:a:0 -c copy out.mp4
  ffmpeg -v error -i out.mp4 -map 0:a -c copy -f md5 -        # 与 published.mp4 算出的值必须相同
  ffprobe -v error -select_streams a:0 -show_entries stream=start_time,duration -of csv=p=0 out.mp4
  ```

- 缺失的派生素材显示醒目的占位层（例如带标签的红色层），不静默回退到另一画幅的素材；终检从编码成片
  抽帧，确认没有残留占位。
- 改动多个版本共用的渲染代码后，从新代码渲染关键帧，与已发布成片逐帧比 PSNR。参考帧按帧号抽：
  `-vf "select='eq(n,F)'" -vframes 1`（F 为帧号）；用 `-ss` 按时间换算常差一帧，有运动的画面会掉到
  17–23 dB 造成误报（观测实例：改为按帧号抽后 35–47 dB，属编码损失加颗粒的正常范围）。
- 两个画幅共用同一套场景代码、首发画幅已经发布时，派生前先给已发布画幅拍一套静帧基线：在改动共用代码之前、
  用产出已发布成片的那一版代码拍，按固定间隔取时间点，用渲染器直接出的单帧，不经视频编码（Remotion 用
  `npx remotion still <composition-id> out.png --frame=<帧号>`，其他引擎用各自的单帧导出）。先在同一时间点
  重拍两次，确认逐像素零差异，证明静帧渲染是确定的，回归门禁才能要求“没有一帧判为变化”。这和上一条
  “新代码渲染帧对已发布编码成片比 PSNR”是两种比对：PSNR 证明基线代码仍能复现已发布成片，静帧门禁证明
  之后的修改没碰已发布画幅，互不替代。每帧按“像素差超过多少级、这样的像素占比超过多少”判是否变化，两个阈值写进报告。第二画幅的修改
  只进按画幅区分的代码（它自己的布局常量、只在该画幅生效的样式、按画幅门控的场景内动画时间；剪辑时间码仍不动），不改共用的默认值；
  每组修改后重拍改动所在场景对应的时段，判断不了影响范围时重拍全部基线帧，必须全部判为未变化，有变化先查清
  原因再改下一组。观测实例（Skill 介绍片）：每 1 秒一帧共 278 帧；按 8 位 RGB，任一通道差超过 24 级的像素
  占比超过 0.2 % 判为变化：

  ```python
  d = np.abs(a.astype(int) - b.astype(int)).max(axis=2)  # a、b：同一时间点的两张 8 位帧
  changed = (d > 24).mean() > 0.002
  ```

- 改了两个画幅共用的代码（例如重录旁白后整轮重排场景），每一轮自检都同时拍两个画幅；来不及就在汇报里
  写明第二画幅这轮没查，并单独排一轮第二画幅复查，不能拿一个画幅的快照当整轮通过。观测实例（Skill 介绍片）：
  重录后的整轮重排只拍了竖版做自检，横版在同一轮里悄悄坏了：一个调色擦除动画在横版不生效（横版布局数据里
  的动画参数类型写错），多处证据截图过小、半屏空白，网页截图被右缘截断。
- 新画幅重新定义安全区和每一层文字的位置（按变体取一套常量），不直接缩放原画幅版式。把每种文字样式
  出现的关键帧（片名、章节卡、长字幕、结尾、logo 卡）拼成联系表，查顶部时间水印、角标、日期、章节卡
  有没有互相压叠，字幕会不会被播放器控制条挡住。观测实例：B 站播放器悬停有控制条，字幕抬到距底边
  96 px、两侧各留 240 px；章节卡与日期条相撞，下移后解决。

## 3. 各类素材怎么换画幅

- 360 镜头：重投影，不裁切，见 [`360-reframe.md`](360-reframe.md)「派生 16:9」。
- 手机视频：方向看 ffprobe 的旋转元数据，不只看编码宽高；1920×1080 的文件可能带 −90（其实是竖拍）
  或 −180（横拍倒置）。竖拍素材转横版用“居中 + 自身模糊底”；横拍素材改用整幅时，把原来裁掉的两侧
  当新内容整段复核。
- 照片：先用模板匹配在原图上定位原画幅已批准的裁切框（观测实例：匹配度 0.956），把新露出的区域标出来
  复核；复核完成前默认用“已批准画面居中 + 模糊底”，不露出新内容。放大倍数尽量不超过 1.3，超过时看
  1:1 效果再定（观测实例：4:3 原图铺满 16:9 要放大 1.33 倍，看过可以接受）。
- “脸在横版里不明显大于竖版（约 1.2 倍以内）”只约束视频重取景和裁切放大（见 360-reframe「派生 16:9」）。
  原图本身是横图、竖版整张放在模糊底上的照片（例如合照），横版整张铺满是自然呈现，不要为套这条规则缩成小窗。
- 遗照、病房、儿童等敏感画面在新画幅必然放大可辨认的脸时，不硬取景，直接用原画幅已批准画面居中垫模糊。
- 旧照片的时间戳、拼图边和平台水印顺带移出画面，放大后按 1:1 检查角落。

## 4. 平台文件的码率

- 视频号：平台建议码率 ≤ 10 Mbps（以 `lov-media-publisher` 的预检为准）。平台 MP4 一次按上限出：CRF 加码率
  上限（例如 `-crf 20 -maxrate 9M -bufsize 18M`）、`-movflags +faststart`，并显式写
  `-colorspace bt709 -color_primaries bt709 -color_trc bt709`；渲染完立即核对码率，不等上传预检报
  `video_bitrate_high` 才补。观测实例：crf 18 的渲染输出约 20 Mbps、2.1 GB，被预检拦下；按上面的参数、
  High@4.1、GOP 60、音频 copy 重压约 10 分钟，得视频 8.36 Mbps、857 MiB。当时只写了 colorspace，回读
  primaries 与 transfer 为 unknown，所以三项都要写。
- B 站：投稿页只限大小和时长，没有码率上限，且会对每条投稿重新转码；直接上传渲染出的原码率 H.264/AAC MP4，
  不为码率或体积重压。遇到预检警告先查它是脚本默认值还是平台规定。上传与回读规则以 `lov-media-publisher` 为准。
- 封面：一个视觉一次派生各平台需要的比例（视频号 3:4 单槽；B 站 4:3 与 16:9 两个槽），见
  [`cover-and-title.md`](cover-and-title.md)「改编作品与叙事片封面」。

## 5. 派生版本的质检

- 只换画面时，用时长、响度、真峰值与首发版本完全一致证明音频没被改动，并用 `ffmpeg -xerror` 完整解码。
  观测实例：两版都是 827.05 秒、−16.0 LUFS-I、−3.0 dBTP。音频是原样复制时，两份文件的音频流哈希还必须
  相同（命令见上文「同一条时间线，只换画面与版式」）。
- 画面从最终编码文件按固定间隔抽帧看完全片（观测实例：每 10 秒一帧，84 格），重点查字幕层、品牌层
  是否缺失，是否残留占位帧。
- 新画幅按 [`delivery-contract.md`](delivery-contract.md)「发布前隐私扫描」再扫一遍（检测器逐帧、人工联系表
  不低于 5 fps），重点看新露出的区域。
- 打码框按每个画幅的实际裁切各自定、各自逐帧核对：第二画幅更宽时，可能露出首发画幅裁掉的内容。技法见
  [`remotion-pipeline-pitfalls.md`](remotion-pipeline-pitfalls.md)「打码」。

## 6. 首发前扫描与已发布版本

- 首个平台版本发布前按 [`delivery-contract.md`](delivery-contract.md)「发布前隐私扫描」扫完全片（检测器逐帧、
  人工联系表不低于 5 fps）。派生复核
  常会翻出首版的问题：观测实例中，派生第二个画幅时才发现首版抽帧漏掉的一处不到 1 秒的敏感画面，以及
  镜头备注“只用 0–5 秒”与实际渲染不符。
- 已提交或已发布的版本发现瑕疵时，按 delivery-contract 同节处理。
